## 当前能力与主要缺口

### 技能寻址尚未连到完整业务闭环

当前静态索引有 79 个真实 Hermes 技能，补充标注覆盖 14 个，关系图有 8 个档案、12 条边。三个内置执行器对应两个业务契约：CSV/XLSX 去重与 JSON 空白规范化。索引文件存在不代表这 79 个技能都已经执行验收。

[推荐入口](/Users/audrey/项目/rpe-harness/src/rpe_harness/runtime.py:111)调用 CapabilityRouter；[生产执行](/Users/audrey/项目/rpe-harness/src/rpe_harness/runtime.py:218)直接使用冻结计划的 executor_id，没有经过冷技能发现或推荐链。外部技能推荐不能直接执行，是正确的权限边界；下一步可以在推荐与契约之间增加宿主适配及验收，而无需取消这个边界。

[非 L0 路径](/Users/audrey/项目/rpe-harness/src/rpe_harness/capability.py:218)仍遍历全部技能并评分排序，尚未证明库增长后的质量与成本曲线。旧 500 技能压力测试为模拟库，旧冷技能实验从同一 metadata 构造场景与任务；这些不能代替独立真实任务。1.5 的[休眠检查](/Users/audrey/项目/rpe-harness/src/rpe_harness/experiments/unattended_sequence.py:101)是将一条已知 JSON 经验置为 dormant，再按已知精确 key 查回；它证明索引保留，尚未证明自然任务能唤回冷技能并正确执行。

### MCSI 有来源引用，缺少信息不足时的恢复机制

[MCSI 当前实现](/Users/audrey/项目/rpe-harness/src/rpe_harness/mcsi.py:81)有类型校验、事实与约束字段、来源引用和 16 KiB 拒绝上限。500 字符只是 is_minimal 提示。source_ref 保存 ID 或内容摘要，并没有自动解析原始上下文、检测信息不足、补取上下文后继续决策的链路。

冻结文件计划对既有契约的必要参数做了实质校验；这不等于通用多节点状态已经充分。后续应按能力定义必要事实、来源与新鲜度，缺失或冲突时按需读取原事件或请求补充，再继续原任务。

[接口文档](/Users/audrey/项目/rpe-harness/docs/mcsi-spec.md:59)仍写“<500字符”“必须保留 source_ref”“可请求补充上下文”。应同步实际字段、限制和未实现的恢复流程，避免把设计原则当成现成能力。

### 飞轮已有治理，缺少真实探索驱动的候选竞争

默认 cycle 从已验证计划整理声明配方，并生成七类结构化诊断。[代码](/Users/audrey/项目/rpe-harness/src/rpe_harness/evolution/cycle.py:136)表明，这些诊断主要是带持久证据的模板提案。外部 proposer 或独立 CLI 可以提供 Python 候选，再走独立验收及自动激活。

1.2 已有[真实 CLI 代码生成演示](/Users/audrey/项目/rpe-harness/reports/v1.2.0/1.2开发与验收报告.md:66)，不能说代码生成从未发生。当前仍缺一个持续提案工人：从真实失败或重复探索轨迹选择问题，调用本机 Agent 生成有针对性的候选，在固定预算和新任务上与已有方案竞争。默认配方仍使用既有 producer，因此配方增长本身不证明学会了新算法。

自动验收、生产独立 oracle、隔离、同计划回退和版本回滚已经是可观察的机制成果。[1.5 报告](/Users/audrey/项目/rpe-harness/reports/v1.5.0/1.5验收与进度报告.md:52)准确区分了外部候选自动部署与自主算法创作。

### 长期无人值守有明确的维护断点

[cycle 的历史预算](/Users/audrey/项目/rpe-harness/src/rpe_harness/evolution/cycle.py:169)统计所有运行，第 101 条就会在任何维护写入前拒绝继续。这对有界批次是诚实的限制，对持续积累的无人值守产品则是实质缺口。

需要将“单次处理预算”与“系统累计历史”分开：有游标的分批维护、未处理队列、可追溯的证据归档、紧凑索引及引用保留，确保预算耗尽后能在后续周期继续。不能简单取最近 100 条并隔离所有旧版本，因为活动版本仍可能引用较早证据。调度、重试与提案去重也应接受长序列验证。

### 原生对照尚不能归因于学习

1.2 [36 次真实对照](/Users/audrey/项目/rpe-harness/reports/v1.2.0/1.2开发与验收报告.md:100)中，支持任务通过率为原生 9/12、集成 12/12；整体为 12/18、15/18。这些实验对应旧安装快照，最终 1.2 包另有五份生产源码差异和功能补测，不能外推当前 1.5 性能。两组工具策略不同，原生六次超时用量不完整；成功配对成本存在选择偏差。结果支持该旧快照在固定任务集下的整体集成策略，不能推出全量节省或飞轮收益。

1.5 留存证据为 801 项 pytest、28 个无人值守独立进程和两次真实 Hermes JSON 候选调用；它验证本版功能，没有新增公平原生对照或学习消融。接下来需要控制同一工具策略，分别测“无经验”“声明配方”“程序候选”，把首次探索、索引维护、验证、失败回退的成本一起计入，并在留出输入上复用。进程重启与单会话续接已有证据，换模型或换宿主接续仍需另外验证。

## 阿卡夏融合取舍

**继续采用 RPE 单内核加阿卡夏资产层。** 内容寻址、来源签名、能力封装和版本谱系适合承载可积累的能力；RPE 统一实际执行、验收、反馈和激活，避免两套成功判断与版本指针。

旧 [L4 设计](/Users/audrey/项目/progenitor-protocol/docs/L4_EVOLUTION_DESIGN.md:4)本身强调真实使用改变 reputation、留下 lineage、退化触发 rollback，并未承诺自主代码创作。恢复旧平行运行时不会自然填补寻址、状态充分性或学习收益缺口。旧仓适合保留为来源与资产仓，值得进一步吸收的是按能力版本观察真实质量趋势，而非引入第二个执行器管理体系。

## 需要纠正的设计表述

[架构文档](/Users/audrey/项目/rpe-harness/docs/architecture.md:11)把“技能检索成本线性增长”“每次任务都需要 LLM 浏览完整技能库”写成了确定事实。原对话只是提出痛点与研究问题；Hermes 当前官方文档已经说明技能按需分层加载完整内容。应改成待验证的规模、召回与成本问题。[Hermes Skills 官方说明](https://hermes-agent.nousresearch.com/docs/user-guide/features/skills)

“因果图”当前主要是关系、前置条件与场景匹配，没有干预或消融证据。可先准确称其为能力关系与条件检索；只有独立实验支持后，才宣称因果机制带来收益。直接查表、条件索引和宿主按需加载也可以实现原始目标，具体机制由实验选择。

轻量维护可以继续参考 Hermes 的按需加载、归档恢复和变更账本；候选与评估分离可参考 GEPA。社区机制提供实现路径，不能代替本项目的质量验收。[Hermes Curator](https://hermes-agent.nousresearch.com/docs/user-guide/features/curator)、[GEPA 原论文](https://arxiv.org/abs/2507.19457)

另有一个当前静态代码问题：[技能 API](/Users/audrey/项目/rpe-harness/src/rpe_harness/server.py:174)仅按 CSV/XLSX 的 BUILTIN_IDS 判断 executable，因此已注册的 JSON 内置能力会被标为不可执行。应作为接口一致性修复单列，不能与原始研究缺口混为一谈。

## 补充工作的优先级与验收

以下是设计审核建议，尚未实施；完成标准按原始问题定义，不按新增文件、提案或测试数量定义。

| 优先级 | 补充工作 | 验收应回答的问题 |
|---|---|---|
| P0 | 对齐设计表述、接口文档及能力展示 | 文档与 API 能否准确区分发现、可执行、已验证、已激活和研究假设？ |
| P1 | 真实能力寻址闭环，含新增技能同步与休眠再验证 | 自然语言任务能否发现真实技能，经宿主或契约适配实际调用并验收；冷技能恢复后能否完成任务？ |
| P1 | 按能力定义必要状态，接通来源解析和信息补充 | 缺条件、冲突历史或环境变化时，压缩状态能否发现不足并恢复正确决策？ |
| P1 | 持久分批维护与受限 CLI 提案工人 | 超过 100 条运行仍能持续处理；真实反馈能否产生针对性的提案、候选竞争与自动回滚？ |
| P1 | 原始目标的独立实验 | 不同库规模、冷热比例与相似技能密度下，正确调用率、误报、延迟和全量成本如何变化；学习后是否优于未学习？ |
| P2 | 第二宿主和模型替换接续 | 同一任务、经验与能力能否被另一模型或宿主继续使用，兼容错误是否可观察并恢复？ |

技能规模可先以现有真实库建立基线，再按可用真实资产增加规模；100/500/2000 是实验档位建议，不应通过复制同一技能来冒充覆盖。可以用标明为合成的干扰项测索引压力，但正确调用和业务验收仍须独立真值。

当前最有价值的下一步是：**在同一真实任务序列中，把“发现能力 → 必要状态 → 实际执行 → 结果反馈 → 形成候选 → 留出任务复用”串起来，并测质量与总成本。** 新文件格式和 JSON 签名分发可以排在这条验证之后。
