## P2 — Native acceptance could certify modified helper bytes (resolved)

Primary locations at discovery: `experiments/skill_comparison.py:239-243,275-302`; launcher `integrations/hermes_session.py` writable session-home scope. The native gate checked original helper bytes after the session and accepted a direct successful terminal argv. Session-home files were writable, so the native actor could chmod/change xlsx_read.py, execute modified bytes, then restore original bytes before the final gate. The record would claim the pinned original helper ran even though different bytes actually ran.

Bounded no-model proof: `native-invocation-probe.json` shows pinned/final SHA `5ab31b1b417efea11a8af7b15c6aa5f26d6d966effefaa19af604c1fa0ca0916`, actually executed SHA `6975d1273e347cbe57d3ae08454c1b67b5745a08400a1bb8af04177fcc9deac4`, exact output, and `gate.verified=true`. This is a controlled gate probe using an actual subprocess and controlled durable observations; it is not a model session.

The first fix denied writes to home/skills and skill-config.json. A separate real macOS sandbox probe (`protected-ancestor-probe.json`) showed that renaming home to home-moved, modifying the helper there, and renaming it back bypassed path-only protection. Thus direct write/chmod/unlink coverage alone was insufficient.

Final fix: sandbox_profile now denies writes to protected trees/files and to each literal ancestor within a writable grant, including session-root/home where applicable. Launcher supplies both materialized skills and the immutable configuration. Independently repeated ancestor probe (`protected-ancestor-green-probe.json`) now records PermissionError on parent rename, ordinary history writes allowed, and original helper bytes preserved. The hardlink probe was already denied (`protected-link-probe.json`), so no hardlink issue was reported. Supplied root regressions separately exercise direct write/chmod/unlink. This P2 is resolved in the current guard.

## P2 — Valid catalog exceeded the host's configuration budget (resolved)

Primary locations at discovery: `integrations/hermes.py:552` and `integrations/hermes_skills.py:361`; launcher serialized all materialized entry metadata. Catalog accepts up to 2048 skills and an 8 MiB manifest, but both host consumers rejected skill-config.json above 1 MiB. Therefore a supported catalog could sync/materialize normally yet neither native observation nor skills workflow could start.

Bounded no-model proof: `catalog-host-budget-probe.json` synced/materialized 451 valid skills, with a 1,224,119-byte manifest and 1,403,647-byte host config, then register() raised `invalid native skill observation config`. This does not claim search-quality scale or use copied skills as execution acceptance.

Final fix: launcher serializes only six identity/hash/path fields and explicitly bounds the config at 8 MiB; both observer (`hermes.py:552`) and workflow (`hermes_skills.py:361`) use the same 8 MiB consumption bound. Independently repeated the original 451-skill probe: the original 1,403,647-byte config now registers with the observer and is read successfully by the workflow (451 entries). The corresponding compact launcher serialization is only 140,625 bytes. Evidence: `catalog-host-budget-green-probe.json`. This P2 is resolved. No copied-skill scale or model execution claim follows from this budget regression.
