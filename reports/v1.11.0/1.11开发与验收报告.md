# RPE-Harness 1.11 开发与验收报告

1.11 已接通公开自然语言入口、真实技能选择、冷技能召回和显式来源恢复。冻结的四对正式任务中，RPE 完整链通过 **1/4**，Hermes 原生通过 **0/4**；但只有一对达到可比条件，`comparison_ready=false`，本轮不能证明总体质量或总成本收益。正式结果之后，另用一次新模型会话走通了冷技能、来源恢复、原 helper、确认、执行和重放的组合链路；这项补验单列，未改写正式成绩。

状态：功能与有界验证完成；专属测试目录已清理。安装包、报告和证据正在完成本地分支交付及托管工作树归档。

## 解决了什么

公开 `review draft` 原先存在生产者与消费者字段不一致：宿主验证器返回 `verified/proposal_verified`，CLI 却检查另一字段，真实提案可能被显示为缺上下文。1.11 修复这条公开路径，并验证 `draft → show → confirm → run` 的实际子进程衔接。用户直接提供自然语言；确认面向展示后的完整提案，模型仍没有确认权限，确认本身也不执行任务。

配置真实技能目录后，起草流程增加“发现、显式选择、原生加载”。发现查询真实元数据，不先按 XLSX adapter 把其他技能过滤掉；模型可选择返回候选或明确选择 none。选中受信适配器后，父层绑定原始技能、目录快照、技能和 helper 摘要。冷技能只在独立 Hermes HOME 的副本中归档，由真实 `restore_skill` 恢复，再经原生 `skill_view` 读取；日常技能目录不参与归档或恢复。

发现不等于执行许可。独立审查发现，未信任技能即使关闭预处理，原生加载仍可能触发依赖处理；修正后，这类技能仅供元数据发现，直接进入不可执行提案，不激活其加载或安装副作用。执行仍限于已登记能力及受信字节，没有给任意技能或脚本新增权限。

来源恢复复用已有 ContextStore。可信调用方显式选择附件，父层导入当前实际会话，模型只接收白名单事实和短引用；原始请求逐字保留，不转发完整聊天，不扫描日常记忆。提案记录来源引用、逐字段出处和恢复证据；确认、执行及 worker 启动前重新检查来源 hash、session、当前可用性和技能绑定。模型遗漏的字段不会被父层悄悄修进原始 draft，缺业务决定、冲突或引用不匹配均继续阻断。这里没有新增通用来源过期策略，实时重验不等于任意时效性保证。

## 与原初方向的关系

RPE 继续作为独立的执行、验收与持久记录内核，Hermes 作为首个宿主，提供真实模型调用、技能管理和原生工具。已有的目录、ContextStore、不可变提案、文件绑定、确定性执行器和独立 oracle 被接到同一公开入口；没有重建分类器、通用记忆平台或常驻服务，也没有合并旧 Protocol、Registry 仓库。Python 运行依赖仍只有 openpyxl。

这使“能力可找到、冷技能可恢复、下游只拿必要事实”在现有任务范围内形成更直接的工程链路。它尚不证明技能数量增长后的寻址收益、跨模型或跨宿主连续性，也不证明经验学习已经带来净收益。当前可执行范围仍是表格按明确键保留首条去重、JSON 结构空白规范化和通过已审核原 helper 检查 XLSX；任意新技能执行不在本轮范围内。

## 冻结的真实对照结果

模型为本机 Hermes 配置的 Xiaomi `mimo-v2.6-pro`。协议包含一对 pilot 和四对新正式任务；正式任务由三项生产任务及一项缺键边界探针组成。两臂获得同一当前原文、输入、授权来源事实和适用的真实技能供给，使用共同预算；原生保留自己的工具，RPE 从公开 CLI 起草。审阅器只接受或拒绝原候选，不替模型修复合同，不向模型补正确答案。评分接受能力本身已保证的保留行为，不额外强求原文未要求的冗余 flag。

## 正式结果之后的一次组合补验

正式数据封存后，最终修正补充了标量参数兼容和原 helper 实际执行回执，并完成相应定向验证。nullable schema 并未被证明是先前失败的根因，本报告不作该因果归因。

补充协议只授权 **1 次新模型会话**、最多 5 次 API、8 轮和 180 秒，不修补草稿、不第二次尝试，也不回填正式得分。新输入只在附件中指定 `mode=rows`、`sheet=复核`，当前自然语言没有重复这两个值。真实运行验证了：冷技能恢复和原生加载、来源事实恢复、提案引用及绑定、模拟语义审阅后的确认、调用原始 helper 生成正确 JSON、输入保护，以及同一确认的确定性重放。

补验结果 `verified=true`，`cold_skill_restore_verified/source_restore_verified/original_helper_artifact_verified/deterministic_replay_verified` 均为 true。提案 ID 为 `0469c7d468b2db94e5938534e99c807b5b444ab37ad3b7c373f881a208b3d199`，产物 SHA256 为 `306d0bce232d63450d565c769d4d21bea29a670cdac64db9d21b63cf716054b1`。该会话观测完整，共 **5 次逻辑 API、10,559 tokens、53.49 秒**。

审阅者标签为 `simulated_postfix_semantic_reviewer`，`human_confirmation_verified=false`。这证明一个新输入上的真实工程组合链路成功，不是用户真人审阅验收，也不是新增的一对原生比较。补验是在正式失败后进行，不能用这个单例替换正式结果或推算一般成功率。补验记录见 [补验协议](post-acceptance/protocol.json)、[真实结果](post-acceptance/result.json)、[提案与宿主回执](post-acceptance/draft.json)、[执行](post-acceptance/execution.json) 及 [重放](post-acceptance/replay.json)。

## 工程验证与证据边界

公开 CLI、真实已安装 Hermes SDK、技能目录、归档恢复、来源引用、越权及篡改拒绝、确认与执行重验、幂等重放均有定向验证。来源集成中还修复了有效附件执行时的数据库写锁冲突：来源新证据先于执行声明事务写入，事务内继续复查并发声明，worker 启动前再次重验。

完整回归原始运行记录为 **1,698 passed、1 failed**；失败涉及沿用旧合同的 mock，不能删去这次失败记录。随后针对修正与补充运行了 **121 项**检查，该阶段按测试身份去重覆盖 **1,717 项**，不是将 1,698 与 121 直接相加。最终标量参数和 helper 回执两项修正又有 **83 项定向检查通过**；它们不能冒充修正后的新一轮完整回归。

按当前收集的用例身份合并完整运行、受影响补测和最终标量 SDK 线缆验证，**当前 1,720 项源码用例全部有通过记录，另有 3 项子测试**；删除或改名的旧身份单列，未虚增计数。独立 wheel 安装的测试按模块、类及参数去重后为 **147 项通过**；最终包另运行受影响的 55 项检查。最终 wheel、独立安装的 80 个模块与补验源码逐字节一致。合并依据及原始 JUnit 见 [验证账本](validation/test-coverage.json) 与 [最终安装包证据](validation/final-wheel-evidence.json)。这仍是一次完整回归加定向补测，不冒称最终版本重新完整跑绿。

公开证据保留夹具、当前原文、授权来源、实际候选、产物和不可变成本记录。离线验证重新核对业务产物、来源文件、语义评分、阶段账本、分臂聚合、配对和正式冻结关系；它验证记录的一致性，不是独立第三方运行证明。清理前离线复验已通过，见 [清理前记录](verification-before-cleanup.json)。清理后的独立 runtime 复验见 [清理后记录](verification-after-cleanup.json)，复验脚本 [verify_delivery.py](verify_delivery.py) 不调用模型、不安装软件、不写运行状态。

## 后续重点与本地交付

下一步优先提高现有入口的稳定可用性：减少 `comma` 这类有限标量表达错误和逐字引用错误，保持原文、显式事实与实际执行合同清楚对应；补齐原生草稿和冷召回的真实观测，再用新的、有界且冻结的配对验证收益。正式负结果保持不变。无需为这些问题增加通用框架、分类器或更宽的技能执行权限。

来源摘要只证明内容未被替换，来源语义真实性仍由可信宿主和审阅者负责；模型引用覆盖也不证明理解完整。当前结论限于单模型、单宿主、少量既有能力与定向输入，没有验证真人审阅负担、长期积累或跨模型持续复用收益。
