## Four reproduced candidate findings

1. **P1: activation can switch after its checked certificate changes.** `src/rpe_harness/evolution/candidates.py:281-291` reloads/checks the proposal before acquiring the SQLite write transaction, then never rereads that certificate in the switching transaction. A fault injected immediately after the second `_certificate` return changes `validation_json` to invalid JSON without updating any hash. `apply_candidate` still returns `applied=True` and switches the active pointer. This is the design's explicit post-check tamper window. Acquire `BEGIN IMMEDIATE`, reload and check the exact proposal/version/certificate and CAS base inside that same transaction, then switch. Keep file-content checks and the production artifact oracle independent. Re-test concurrent mutations as well as deterministic faults.

2. **P2: malformed active certificate bypasses quarantine and builtin fallback.** `src/rpe_harness/evolution/candidates.py:325-326` calls `get_active` before entering its recovery `try`. `EvolutionStore._proposal` at `store.py:183-185` parses JSON there. Replacing an active certificate with malformed JSON makes `prepare_candidate` raise `JSONDecodeError`; the normal run fails/rejects instead of clearing/quarantining corrupt active state and using the builtin producer under the same plan. Put active lookup/record parsing inside the guarded path, and record pointer corruption even when a usable version object cannot be reconstructed.

3. **P2: rollback cannot recover to builtin when the previous revision is corrupt.** `src/rpe_harness/evolution/candidates.py:367-372` checks the dormant predecessor certificate and artifact but propagates validation/hash errors. After A and then B are activated, corrupting A's code makes `rollback(B)` raise `ValueError('candidate artifact hash changed')` and leaves B active. Quarantine the unusable predecessor, then atomically rollback to registered builtin, retaining reason and snapshot evidence. A known valid predecessor should still be restored normally.

4. **P2 hardening: complete fixture evidence is not validated at application.** `_certificate` at `src/rpe_harness/evolution/candidates.py:242-252` checks `passed`, public hashes, revisions and version identity, but not the expected complete fixture-name/split/check set. Clearing `checks` and setting both counts to zero, then consistently recomputing the report hash and version ID in SQLite, is accepted by `apply_candidate`. Validate the strict certificate schema, expected exact suite, positive train/heldout counts, every fixture predicate, proposal identity and allowed activation scope. **Threat qualification:** this reproduction assumes write access to the trusted SQLite database, which is outside the candidate child's filesystem boundary. Public content hashes detect inconsistencies; they do not authenticate arbitrary coordinated rewrites of trusted state. Do not claim they do.
