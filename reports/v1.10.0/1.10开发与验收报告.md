# RPE-Harness 1.10 开发与验收报告

状态：1.10本地验证版已交付，功能、工程验收、测试清理与工作树归档已完成。自然语言入口需要审阅；总体质量和总成本收益尚未成立。

## 这次解决什么

以前的1.9需要完整、严格的JSON来源，用户要自己把任务写成机器合同。1.10新增自然语言入口：你直接说任务，Hermes把它整理成可读的要求清单，显示原话、逐项原文引用、建议默认值、执行字段和未解决问题。你确认这份具体清单后，控制器才从不可变确认记录里取合同，沿用原来的确定性执行器和独立验收。模型没有确认工具，也不能借起草阶段执行业务。

这是一道可审阅的理解入口，不是自然语言语义完整性的证明。原文引用只证明出处；模型仍可能漏掉意思，审阅者需要对照完整原话核对。确认前没有业务输出，确认本身也不会启动执行；执行是下一步单独操作。改动原文、清单、输入、目录或能力信任后，旧确认不能继续套用。

## 范围和结构

仍是独立的轻量Harness，Hermes是首个宿主。沿用三种现有能力：CSV/XLSX按明确关键列保留首条去重、JSON结构空白规范化、通过已审核原始helper检查XLSX。没有新增分类器训练、模型自我批准、重试飞轮或常驻服务。Python运行依赖仍只有openpyxl。

主要新增proposal.py、proposal_cli.py、Hermes review入口和独立对照。原有clean严格来源入口保留自己的保证。起草阶段重建实际发送给SDK的消息，只交当前原文和公开合同；下一阶段接收具体草案身份；执行阶段使用已确认机器合同，复用文件绑定、独立oracle、原子发布和持久运行记录。

可信确认属于本地应用边界，actor只是审阅来源标签，并非身份认证。同用户任意代码执行或数据库写权限不属于这个隔离威胁模型。每份确认只能声明一次执行；重放返回同一持久结果，并发不重复发布。父进程真正崩溃后，已消费而无结果的声明保持关闭，需要人工诊断。

## 怎么使用

在仓库执行：

```bash
./scripts/rpe review draft --workspace /absolute/workspace --db /absolute/state.sqlite \
  --text '把 input.csv 按编号去重保留首条，另存 output.csv，保留原文件与顺序。'
./scripts/rpe review show PROPOSAL_ID --db /absolute/state.sqlite
./scripts/rpe review confirm PROPOSAL_ID --db /absolute/state.sqlite
./scripts/rpe review run CONFIRMATION_ID --db /absolute/state.sqlite
```

用户不用手写JSON。交互确认会显示完整审阅并要求输入“确认”；管道输入不会成为交互确认。真正缺键、冲突、无法支持的额外条件或未映射字段都会阻止确认。修改任务需要用完整新原文重新起草，得到新的身份。

## 证据及实际收益

### 冻结的真实模型对照

模型为本机Hermes配置的Xiaomi `mimo-v2.6-pro`。两臂收到相同原文、文件和公开要求格式；原生臂保留自己的工具发现，RPE臂只提供起草工具。夹具审阅器只接受或拒绝原候选，不替模型修合同，不把正确答案发给模型。这里的确认是`simulated_fixture_reviewer`，不能当作真人审阅。

正式比较包含CSV复合键、实际TAB分隔、保留原始数值与转义的JSON、原始XLSX helper四类生产任务，以及缺键、额外求和两种边界任务，每臂各6次起草。结果如下。

| 正式生产结果 | Hermes原生 | RPE review |
|---|---:|---:|
| 要求忠实通过 | 0/4 | 0/4 |
| 获批并完成执行与独立验收 | 0/4 | 0/4 |
| 业务产物正确 | 0/4 | 0/4 |
| 因宿主或观测缺失无法判定草案质量 | 2/4 | 1/4 |

不能把未判定当作已观察到的语义错误。其余失败主要有两类：能力ID或字段映射写错；把固定默认值、执行前提和“尚未确认”误作未解决业务要求，导致可以支持的任务也无法进入确认。两臂各两个边界任务均没有批准或业务输出，但精确要求与拒绝原因的严格验收均0/2，不能把这种阻断全部算成正确理解。

最早pilot的2次起草也失败：原生正确写出草案，但缺少stdout工具ID的证据解析未识别；review遇到模型输出的数组字符串，以及Hermes官方参数转换后的摘要差异。诊断和来源修正另行记录，旧成绩保持原样，没有追改成成功。正式比较使用来源修正后的冻结版本。

正式比较注册摘要为`4401d94dc2ac967720ca3391e1f2e28b58f5cb49662c37a586716ed41919c7f8`，来源代码`aa5d9a5`。原pilot注册摘要为`da795cadba557f39c1baa1153b2106138fa550cb5739c9513c5e6ec4372b8bcf`。公开证据、不可变账本和离线复验分别保存在`pilot-original/`与`public-evidence/`；不混入1.8或1.9的数据。

### 一次契约修正与独立冒烟

正式负结果封存后，仅修正起草工具schema与双方共享说明：能力ID、标志、字段指针和选项给出精确枚举；说明建议默认值、父层运行检查和真正缺失业务决定的区别。纯不支持任务可以选择非执行的`unsupported`。没有清空已有未解决条款、放宽父层检查、增加重试或修复模型文本。官方Hermes本身不执行JSONSchema枚举语义校验；枚举是给模型的公开契约，父层验证仍是执行门槛。

修正后的源提交为`2b525f5`。只追加一对预登记JSON冒烟，注册摘要为`1c920a6ef234a80659e0d9ced7e02311cb6d593e725ffd71bc309304ca45f829`。实际2次起草、0次原生执行，5次API、29807 tokens，整对完整trial累计93.63秒。它是在看过失败后选择的已见任务，不能替换正式成绩或作为总体成功率。

两条新草案的真实调用和来源核验都通过，均为`awaiting_confirmation`，没有缺项、错误或未解要求。精确字段评分仍判0：两份草案都只写`preserve_order`，夹具还额外要求`preserve_original`。独立核验确认这是唯一差异；原文未显式要求后一个标志，JSON能力本身却始终强制保留输入且不得覆盖，与该标志开关无关。因此在这个样本上是评分器对冗余标志的语义误拒，不是新的业务误解。原评分和公开导出保持0，不事后放宽规则或重评。

针对这个差异，独立Codex子代理对照原文作语义审阅，可信父进程以`simulated_semantic_review`身份接受原review草案。为保护原实验数据，先SQLite备份到本轮专用诊断数据库，原proposal ID、摘要、会话、输入和工作目录绑定均不变。没有重新起草或修合同；原DB、成绩、账本和三组公开导出不变，原隔离workspace仅在测量之后新增产物。

补验结果为`succeeded`，运行ID为`358f91274d8d4673949865f81b87f609`。确认本身没有输出；随后控制器按冻结合同执行，独立产物字节与token验收通过，保留`1.20e+2`和原始字符串转义；输入摘要不变、临时子进程全部清理。同一确认重放返回同一结果、同一运行，运行库只有一条run。这证明一个真实Hermes起草的原清单经过独立测试审阅后走通了确认与确定性执行。

该补验不增加Hermes模型调用，不补正式得分，不证明总体理解质量或原生成本优势。Codex独立开发审阅属于开发验证，其token与账单未测；这里的模拟语义审阅与TTY模拟操作都不冒充用户真人确认。公开投影、产物、确认与运行核验见`controller-flow/`，原比较仍保留0完整链。

后测控制器确认执行本地累计耗时0.571314秒，其中确认0.114546秒、执行0.426560秒，额外Hermes模型调用与token均为0，不混入原比较。开发、独立Codex审阅、回归、构建、导出与报告时间不属于任务运行计时，相应开发token和账单未测；也不把缓存token等同于钱。

本轮正式对照没有证明质量或总成本收益。review的已观测token较少，但没有完成同等获批业务结果，不能把低用量写成效率胜出。
