# RPE-Harness 1.7 开发与验收报告

**1.7 的真实学习闭环已经跑通，但还不能说“自学习更聪明、更省”，也不能宣称自然语言入口已能稳定无人值守。此次交付定位为本地实验版。**

用最早讨论时的说法：先真的做任务，把确实做对的经验交给 Agent，让它写一个新工具；另一个验收过程检查工具，检查通过后，再拿新题来使用。这次每一环都有真实记录。CSV 去重能力原本已经存在，新增的是自动生成另一份程序实现的闭环，尚不代表能自动创造任意新业务能力。

本轮采用预登记的公开小型 CSV 任务，在真实 CLI、模型 API 和沙箱中执行；日常业务覆盖和长期无人值守表现仍待验证。

两个 RPE 组分别通过真实 CLI 完成 6 个训练任务，原生组也实际运行了 6 个模型训练会话。Hermes CLI 使用 Xiaomi 的 `mimo-v2.6-pro` 生成 G0，再根据原始代码的实际探测结果和已授权训练材料生成 G1。两份代码都由原生 `write_file` 写出，有 API、工具身份、实际文件内容和参数摘要的关联；原始代码没有人工修补。

G1 通过独立的 13 例资格验收（3 个训练例、10 个独立验收例）及激活重播。随后冻结代码、执行器版本、模型身份和实验条件，完成 8 类未见输入 × 2 次重复 × 3 组的 48 次真实会话。G1 的原始 SHA256 为 `3afd6be78a69caf7b055ae5afb8a69ef0deb7b542593dfd47f7838153cab9c43`，版本为 `adc6c2804d9d6356cef4ed40a28b2b552201f634e6a699eefcf09ca60b4f182c`。

原生流程关联不足不等于产物错误。学习组有一例产物正确且实际执行了 G1，但模型漏填了要求的保留约束，完整契约验收拒绝，所以没有计为已验证复用；内置组的 CRLF 第二次也有约束遗漏。Tab 例子还暴露了把一个真正的 Tab 写成“反斜杠加 t”两个字符的问题：内置组两次及学习组第一次均被参数验证拒绝，未产生要求的产物。输出读取失败时部分原记录的 `source_preserved=false` 是未检查的初值；独立审计另行检查实际源文件，不能把该初值解释为源文件被修改。

两次重复共享各组自己的过去工作区，统计单位是 8 类输入，不能冒充 16 个独立样本。原生和 RPE 的工具策略也不同。这次学习组比内置组多一个正确产物，但不能据此归因于反馈；G0、G1 在公开训练例上都为 6/6，实际训练行为没有改善。学习组生产阶段 token 较少，但计入训练、生成、探测、验收、激活和维护后，比内置组多 **17,959 token**。本次原生组开销明显较高，同时产物正确率最高；这也不能单独证明自学习的作用。

原对照结束后，对两个问题输入另登记了 6 次补验，三个组都使用已有 `required_request` 接口绑定完整任务，没有改生成程序、重评原成绩或声称这些还是未见输入。补验为 **4/6 正确**：Unicode 三组通过，Tab 只有原生组通过；两组 RPE 的前三次尝试仍转义错误，提前被契约准入拒绝。学习组随后改成了正确的 Tab，但已超过预先登记的三次预算，因此继续拒绝，没有调大预算重评成绩。绑定入口并未在本次预算内解决问题。补验使用 187,870 token，全部计入整轮成本，失败也保留。

135 个阶段中保留着一个未完成的旧预约；没有重放它或补记成功。超时请求的缺测没有当成零，中断阶段单独恢复的 39,579 token 只加一次。已知阶段运行时间累计为 3,759.97 秒，缺失阶段的时间仍未知。这些数值是观测到的模型用量和运行时间，不是账单。计费金额、开发与编排 Agent 的完整用量、实测内存峰值未采集；缓存读包含在 prompt token 内，不能重复相加或按普通输入价格直接换算。

两个 RPE 组都实际运行了维护周期。为保留对照条件，维护只生成与验证提案，没有自动替换冻结执行器，前后执行器指针一致。自动启用的 G1 则通过了前述独立资格验收和重播；候选不能批准自己或放宽验证器。此次没有增加长期服务、定时任务、新分类器或新运行依赖。

生产代码提交 `ef92f6b` 的完整回归为 **1,324 项测试和 3 项子测试通过**，没有跳过项；生成入口、真实 SDK 请求字段、文件写入身份关联以及实验控制器经过独立复核。安装包、wheel 和源码的 64 个生产 Python 文件逐字节一致。wheel SHA256 为 `12725219b551812367caff210eeceeffdfd3dcbcafd3152f56d71b7895ca0d26`。CLI 模型实测使用本机 Hermes；其他 CLI Agent 的清单不冒充运行验收。

可以确认的进展是：真实反馈来源、程序生成、独立批准、冻结及新输入复用都有可核对的证据。下一项应集中处理任务参数绑定和可修正拒绝后的有限重试，再补失败反馈的结构化表达与独立回归；沿用已有契约和错误类型，不增加一套猜测分类器。核心与验证器仍保留独立治理边界，未通过收益验证的候选不应默认推广到日常工作。

公开证据保留原始生成程序、公开夹具、失败及中断摘要、阶段账本和独立审计。导出摘要的私有路径经过替换，包装记录明确说明源摘要在替换前验证；不能把替换后的内容声称为原始签名文本。原始聊天、凭据、私有会话数据库及缓存不在交付范围内。

清理前核对了 2,212 个实际登记的 PID/启动身份，没有存活的匹配进程，按本轮路径查找也没有残留进程；日常 Hermes 数据库未出现本轮会话身份。两个旧仓的 HEAD 与工作区状态保持一致，主项目原有 `reports/design-trace-2026-10-14/` 保留。日常 `.env` 摘要未变；`config.yaml`、授权和数据库相对最初快照有变化，归因未确定，因此没有恢复或覆盖它们。正式实验登记、冻结、补验登记及结束时的配置摘要相同，未检测到正式对照期间的配置漂移。
