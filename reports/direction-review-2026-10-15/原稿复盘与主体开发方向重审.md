# 原稿复盘与主体开发方向重审

日期：2026-10-15。

RPE 基线：`c54f1defe752f67dc868ebb1779e67c8c33a00fc`，本地版本 `v1.7.0`。Hermes 本机源码基线：`e06df9c2eae6901f4c88f464e0ae6e753c0428b8`，现有工作区修改保留。

本次复盘的判断是：项目已形成窄任务域中较扎实的执行与升级治理基础，但研发重心逐渐偏向这些基础，原本最有辨识度的能力寻址与必要状态传递仍未得到充分实现和正面验收。Hermes 本身已有学习、技能维护、按需加载和上下文隔离，RPE 应把新增价值明确落到这些能力之上的业务约束、可达性与可靠性。

本报告延续[上一轮讨论记录](开发方向与最小状态寻址讨论.md)，不覆盖或删除此前判断。它进一步修正了“生成—验收—复用飞轮是原始主线的全部”的概括。建议部分尚未作为新版本的实施授权。本轮没有运行模型、测试或服务；实验数字均按其原版本和范围引用。

### 四模块与四层路由的关系

四个功能模块是任务理解、技能寻址、执行、结果验证（第 3209—3225 行）。四层路由是规则直达、能力分类、条件与关系检索、未知时模型探索（第 3038—3055 行）。两者不能合并成“四个分类器”。原稿仅在第 3044 行提到“小模型或轻量分类器”，没有要求新训练若干模型或启动四个独立进程。

原稿所说的“不携带记忆”具体是：不默认继承全部情景记忆；共享能力索引和必要经验仍然可以读取。缺失、冲突或追溯时应按来源补取。只压缩字符而丢掉业务约束，会直接违背状态充分性的目标。

这些工作有后续明确开发需求支持。问题体现为优先级与验收对象的迁移，不应描述为整个工程毫无必要。执行权限也不应重新交回一个猜测式分类器；下一步需要补分类和寻址，而非撤销契约边界。

需纠正版本叙述：1.2 已有 Codex CLI 生成 CSV 执行器、13 例验收、实际使用和回滚的证据；1.7 新增的是更完整的真实语义反馈、Hermes 原生写入与未见输入复用关联。[1.2 报告第 66 行起](../v1.2.0/1.2开发与验收报告.md:66)已经记录前一闭环。

目前形成了三个主要偏移：

第一，从“能力增长后怎样调用”转向“候选代码怎样安全升级”。后者重要，但不能代替前者。

第二，从“最小状态能否保留任务含义”转向“执行时如何验证已经给定的明确参数”。这加强了后半程，却把最难的自然语言理解和必要信息提取留在上游。

第三，从“多种已有能力的有效利用”转向“同一窄域实现的更精细实验”。CSV/Excel 在原稿中是解释例子。首个落点选择它合理，持续把主要增量围绕它展开，就会让例子逐渐成为产品边界。

### 最值得重视的实现断点

实际执行支持 [tasks.py](../../src/rpe_harness/tasks.py:5) 中的三个明确能力。外部技能只有当前已审核 hash 的 XLSX helper 能获得可信适配，见 [skill_catalog.py](../../src/rpe_harness/skill_catalog.py:296)。技能目录条目增加不会自动扩张可执行业务能力。

寻址存在两个模型：[Runtime](../../src/rpe_harness/runtime.py:34) 加载旧技能元数据与图；[SkillCatalog.query](../../src/rpe_harness/skill_catalog.py:326) 搜索真实快照。它们都还没有形成一份从任务条件到可执行适配的统一能力目录。后备路径仍扫描和排序，不能仅据 L0 查表说明整个库增长后成本稳定。

[bridge.py](../../src/rpe_harness/bridge.py:56) 是字段白名单抽取，不是自动理解长聊天的语义压缩器。[context.py](../../src/rpe_harness/context.py:134) 只定义三个能力的必要字段。当前实际状态上限为 16 KiB，早期 500 字符只是旧目标及检测方法；是否足够必须看约束保留和任务结果。

[lookup_experiences](../../src/rpe_harness/evolution/store.py:205) 目前按精确 key 查询，全 src 的调用点是两个实验驱动。主生产路径按显式计划 executor 和活动版本槽执行，见 [runtime.py](../../src/rpe_harness/runtime.py:223)。这不表示反馈完全无效：被批准的候选确实能改变后续执行。但它还不是通用的“新任务自动找出以往最适用经验”。

[recommend_chain](../../src/rpe_harness/causal_graph.py:116) 只给主技能和 companion 列表，HTTP 明确返回 suggestion_only；没有相应的生产多步计划执行器。现有关系边也没有被证明是统计因果关系。

## 五 现有亮点与尚待证明的亮点

### 已有实现最扎实的价值

**可追溯的业务契约与独立验收。** 当前已支持任务将原请求、输入 hash、明确约束、执行/验证修订、真实版本与产物绑定。模型说完成、文件出现、候选自测通过都不能单独成为成功。这种严格边界对重复的数据任务有实用价值，但覆盖仍以现有适配为限。

**探索与批准分开。** 生成者提出代码，另一条可信验收路径决定能否激活；生产继续按原计划验收，失败可隔离并回退。RPE 应突出这个“批准必须有对应业务证据”的增量，而不是泛称自己有自学习、日志或回滚。

**来源受约束的状态恢复。** 必要字段来自绑定的来源和会话，缺失、冲突和变化明确拒绝，执行前复查。这给功能分工提供了可复用基础，尤其适合减少自由文本摘要造成的静默语义漂移。

**宿主事件到结果的证据链。** 实际 API、tool、receipt、run、plan 与文件能对应起来，允许区别“确实用过”“做出了正确产物”和“按要求完成了整条流程”。这比比较助手总结更有意义。

这些是工程价值，不是算法首创声明。它们也不能证明 RPE 整体优于 Hermes；需要在合适场景中检验收益是否超过额外复杂度。

### 原稿更有辨识度但尚未完成证明的价值

**能力越积累，仍能稳定找到。** 搜索量与常驻上下文有预算，退出活跃上下文的能力仍保留适用入口，新旧版本不会混用，实际任务能得到正确结果。

**必要状态足以驱动下一步。** 节点不需要重复理解全部聊天，仍能保住业务约束；状态不足时能知道不足，并按来源恢复，而不是猜测。

**模型可换，能力可延续。** 更换推理模型后仍消费同一套能力、任务状态和验收标准；新模型不需要重新学习已固化流程。

**经验真正降低后续计算与总投入。** 新输入复用减少重复规划、生成和调试，包含学习、资格验收、维护及失败的成本后，在足够复用量下仍有收益。

上述目标构成一个值得验证的组合方向。现成的渐进加载、tool_search 和 delegate 都应作为起点和对照；给组合起一个新名字不能代替增量证明。

旧亚毫秒路由结果是结构化输入、模拟目录下的内存函数微基准，不能当作“用户表达到真实能力完成”的延迟。当前也没有对照完整上下文与必要状态的任务等效实验。因此最初三个中心主张尚未因这些数字而成立。

## 七 建议收敛的产品边界

建议将主体表述为：**面向持续积累能力的 Agent，提供状态驱动、可追溯的能力寻址与验证接入层。**

Hermes 承担宿主已有优势：模型连接、对话历史、原生技能创建及加载、通用回收整理、普通工具和调度。RPE 读取必要来源，提供明确能力地址、适用事实、版本、执行适配与验收证据。现有代码生成 worker 可以保留为按需提案工具，新增投入应由真实任务缺口驱动。

通用推荐与严格执行应共享能力目录，但诚实区分保证范围：

- 对仅有描述、没有独立业务验收的技能，可以发现并交给宿主使用，结果明确属于宿主执行，不能自动标为 RPE 已验证。
- 对已注册契约和 oracle 的能力，可以进入现有严格计划、执行、产物验收与发布路径。

这样既不会因为没有通用 oracle 就封死所有外部技能，也不会为了扩大“支持数”把普通技能说明变成执行授权。每新增一个严格能力，都须给出相应契约与验收；通用语义搜索结果不替代这些材料。

继续保留 RPE 主项目和单一执行权威，旧阿卡夏仓作为来源与资源参考即可。无需为此次纠偏再合并仓库、另建运行时或恢复 P2P。独立维护价值最终由这层相对原生方案的可验证收益决定。

## 八 有限的推进顺序和停止条件

### 第一项交付 回到原始主线并接通现有三能力

完成统一能力目录和节点接口。当前请求提炼目标、输入对象、约束、必要事实和来源；明确契约直接进入查找，模糊任务才使用现有模型。字段不足、冲突或不支持均明确返回，允许预算内补取和纠正。

复用已有三个能力和 1.7 暴露的参数错误，不增加分类器训练或新的通用执行平台。完成标准是同一任务经过理解、寻址、必要状态、真实执行和独立验收能逐段解释；任务顺序变化不会带入上一任务的隐含内容。

### 第二项交付 证明能力可达性

接入少量有真实用途、存在相近或替代关系的能力，至少让一个不常驻的真实技能在新任务中被正确召回、重验和调用。扩展应通过小型明确 adapter 边界完成；不要复制条目制造规模。

固定查询和可接受候选真值，比较当前 Hermes 原生技能/工具搜索与 RPE 增强寻址。保持业务输入、模型、工具供给、必要权限和最终产物判定一致。对 archived 技能，原生允许使用其恢复入口。分别统计提取、检索、模型补取、执行和验收开销。

如果原生方案已同样可靠、更简单，应复用其检索而不继续扩建专用搜索或图。RPE 可以仅保留业务契约和验收增量。

### 第三项交付 验证跨模型接续与实际复用

让第二个实际模型消费同一份冻结能力和持久状态，完成一条真实两步流程，包含安全边界重启或冷技能再调用。它验证能力连续性；无需同时接入所有 CLI 或开发完整多 Agent 平台。

随后观察固定的一段工作量，只对重复频繁、当前工具不支持或有明确缺陷的任务提出新能力。把生成、失败、验收、维护和恢复成本都计入，观察复用是否回本。固定工具已经足够时不触发再生成。

以上每项都先确定有限任务和预算。通过便冻结交付；失败保留，并据明确缺陷修复相关回归。不能通过扩大训练轮数、提高尝试预算或重评旧任务制造完成。

### 主体进度应采用的指标

1. 适用的已有能力，是否被正确发现。
2. 找到以后，是否实际正确调用并得到合格结果。
3. 冷技能恢复后，是否仍能完成任务。
4. 传递状态是否保留所有关键约束；不足时能否补取。
5. 任务交错和知识版本固定时，行为是否可复现、无串扰。
6. 能力增长后的检索与常驻上下文开销如何变化。
7. 更换模型后，技能与任务状态能否继续使用。
8. 包含维护和失败的累计成本，以及达到回本所需的复用量。
