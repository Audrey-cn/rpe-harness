# RPE-Harness 1.2 design

## Intent and original design

Deliver a standalone Harness whose durable goals, state, capability contracts and verified feedback survive replacing the LLM or host. Hermes is the first host. The original archive's user messages bbb2119d-23c6-40fb-9389-fb0d2dd8aaeb, bbb21a20-b068-4902-9d7d-e070584ee9d8, bbb21d4b-8707-44b7-ae08-6587b5f22763 and bbb217db-60ec-44e7-aa0b-74555e36f93a motivate replaceable models, local procedural skills, reachable dormant capabilities and minimal sufficient state. Assistant suggestions in that archive are hypotheses and background, not current instructions or demonstrated benefits.

The user authorized delivery, CLI agents, real isolated Hermes tests, unattended upgrade proposals and basic automatic upgrades, and asked to reconsider the full original ambition rather than restrict learning to configuration. Architecture therefore separates proposal scope from activation evidence: proposals can target any Harness component; automatic activation depends on an independently testable contract, owned scope, bounded resource use, persistence and rollback. No automatic update of daily Hermes or global skills is part of this release.

## Alternatives and decision

1. Keep classifier/ranking as the execution gate and add prompt memories: cheap but retains false rejection and metadata interference.
2. Adopt a complete self-evolution platform: broader search but adds dependencies/cost and does not solve artifact acceptance; the current official Hermes self-evolution evaluator measures word overlap rather than real tool outcomes.
3. Selected: exact capability contracts and immutable plans, official Hermes middleware for required entry, plus a small SQLite feedback/proposal/version/rollback loop. Reuse existing mechanisms, no newly trained classifier or invented learning algorithm.

## Execution foundation

Add schema_version=2 with event_id, capability='tabular.deduplicate', goal, constraints and execution parameters. Format is probed from the actual regular input file. No task_type or metadata rank grants execution authority. V1 remains accepted through its existing compatibility validation; already saved events replay without reinterpretation. Advisory routing stays separate and cannot execute external skill metadata.

A frozen ExecutionPlan binds capability/contract and executor/verifier revisions, normalized input/output paths, original input SHA256, key_columns and constraints tuples, sheet, keep, encoding and delimiter. Harness creates it before running any writer and persists its SHA256 in steps. Writer metadata cannot replace requested keys, format, input hash, destination, sheet or constraints. Independent verifier and publication use the plan and recheck source/staging hashes; producer counts are reporting only. Existing rejection, no-overwrite and atomic publication guarantees remain.

## Real Hermes required entry

Use the installed official llm_request and tool_execution middleware; do not patch daily Hermes. A strict isolated home sets tools.tool_search.enabled=off, exposes only rpe_harness, sets parallel_tool_calls=false and sends named tool_choice=rpe_task until a linked, acceptable durable terminal result. Afterwards send tool_choice=none for the final summary. Optional mode remains available for scientific comparison. Provider rejection or ignored policy yields failed/unverified, never silent downgrade.

Expose a small business-parameter tool schema that constructs v2 internally; retain legacy {request: v1/v2} handling for API compatibility, not as the default model schema. A stable trusted entry ID prevents new model event IDs from duplicating work. Optional CLI --request anchors the exact user contract and source hash; natural-language-only mode verifies the resulting contract but cannot prove correct intent extraction. Mismatching args cannot unlock the entry. Invalid parameters can be corrected within a fixed attempt limit.

Record actual request policy fields and schema hash without messages/credentials. Bind real call/turn/API IDs via tool_execution ContextVar; receipt, returned event and post_tool call retain receipt/run links. One shared acceptance gate requires the actual policy, real call/receipt/post-tool/run association, matched contract, freshly checked artifact hash and independent verification, complete observations and cleanup. Session completion alone is insufficient.

## Lightweight learning and evolution

Use SQLite feedback, indexed experiences, proposals and immutable component versions. Collect real durable runs and host failures, retain source run references, input/plan/revision hashes and structured outcome codes. External reported usage, model summaries and ranking confidence never constitute verified feedback. Duplicate observations and proposals deduplicate; lessons remain compact and dormant entries retain lookup keys. Invalid/stale candidates enter quarantine rather than deleting historical evidence.

An unattended cycle always generates structured upgrade proposals from recurring failures and verified workflows even when no model is available. Proposals cover contracts, discovery policy, recipes, Python executor variants, host adapters and core/verifier changes; include evidence, expected behavior, baseline hash, test requirements, budget and rollback. A pluggable proposer can supply richer code candidates. Candidate generation and candidate acceptance are separate.

Automatic basic upgrades include validated owned declarative recipes and pure CSV executor variants for the existing deduplication contract, rather than only JSON settings. Code is content-addressed and executed in a bounded child filesystem/network sandbox. It does not change the independent verifier, capability permissions, dependencies, daily state or installation. Fixed manual fixtures plus held-out counterexamples check first-record semantics, Chinese/leading zeros, quoted multiline keys, missing columns, source preservation and no-overwrite. Every later production artifact is verified against its original plan too. Activation requires complete fresh validation evidence, exact code/contract/verifier hashes and compare-and-swap of the base version; persist the snapshot and intent before switching. Failure leaves the previous pointer, or quarantines the bad revision and returns to the registered built-in executor. CLI supports list/show/replay/apply/rollback and an unattended cycle; no recurring job is scheduled without a user request.

Core source patches and new capability/verifier proposals remain first-class persisted artifacts, not discarded topics. Their automatic activation requires an external trusted acceptance suite adequate for that new contract and a release/scope policy; this release does not pretend existing CSV truths establish arbitrary new capabilities or permit a candidate to approve its own weaker verifier. This is an evidence limitation, not a permanent architectural exclusion.

## Recovery

Preserve idempotency of successful work. Retry only a stopped failed/interrupted pre-publication attempt when the original input SHA is unchanged and output is absent; link the new attempt to the original, bound attempts, and do not overwrite. Publication-started/unknown outcomes remain interrupted and require explicit reconciliation; never silently mark them successful. Candidate failure can fall back before publication only under the same frozen plan and with recorded quarantine/recovery evidence.

## Evaluation and release

Pre-register three independent repetitions of six paired tasks (36 sessions), alternating arm order, same input/prompt bytes, model, observed response model, compatible Python, timeout and observer. Strict policy is intentionally part of the integrated product; disclose request-policy differences. Save all attempts/timeouts, use the same external manual oracle, and report incomplete usage as unknown. Do not call independent repeats a stateful conversation; add a separate continuation/entry-reset check if implemented. No token saving, causal graph or learning benefit claim without observed support.

Run real failure probes for receipt persistence, child failure, owner kill, pre/post-publication interruption, lost response/replay, observer failure, host failure, candidate validation/activation crash, corrupt version and rollback. Keep probes, histories, logs, credentials copies, venvs, caches and processes under one owned root. Record ownership and compare daily config/source at start/end; investigate auth/state changes read-only without rollback. Preserve source, release package, synthetic fixtures and compact scrubbed evidence. Python >=3.10; product dependencies remain only openpyxl>=3.1.5,<3.2.
