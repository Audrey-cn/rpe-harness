# RPE-Harness 1.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement task-by-task; independent workers own separate files.

**Goal:** Reliable verified entry plus a lightweight evidence-driven evolution loop, real recovery and repeated native comparison.

**Architecture:** Exact contracts create immutable plans; official Hermes middleware gates entry; SQLite stores feedback, proposals and versioned local recipes/executors. Acceptance and rollback stay independent of candidate generation.

**Tech Stack:** Python >=3.10, sqlite3, openpyxl, installed Hermes plugin middleware and macOS sandbox-exec.

**Spec:** ../specs/2026-10-14-rpe-v12-design.md

## Global Constraints

- Product dependencies remain only openpyxl>=3.1.5,<3.2; no newly trained classifier.
- Only registered capability contracts authorize execution; metadata, learned text and model summaries do not.
- No modification to daily Hermes source/config/auth/history/services/shared cache.
- All live tests use the explicit turn-owned root; every child is owned and bounded.
- Proposal scope covers the whole architecture; basic automatic code activation is only for objectively tested, sandboxed existing-contract executor variants. Never let candidate changes weaken their acceptance gate.

## Review Focus

- A writer substitutes a different key, source, sheet or destination: plan-bound verification rejects and does not publish.
- Middleware swallowed exception/provider ignored named choice: gate fails despite model saying success.
- Successful tool response lost then replayed: same durable run/artifact, no second execution.
- Candidate code or validation certificate mutated after checking: hash/CAS fail, prior version preserved.
- Crash around publication or activation: uncertain outcomes remain explicit; rollback evidence is durable and unrelated processes survive.
